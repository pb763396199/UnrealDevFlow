## 复盘哪一段

从 `395a262`（0.2.0 发布之后）到 `6d8e4fb`（0.3.0 发布），八个提交，两个任务加一次发布：
`branch-naming`（分支命名）和 `main-repo-index-pollution`（暂存区污染）。

不包括更早的 `tidy-cli-surface`，那一段有自己的复盘。

## 经过

用户要求「在真实 AesWorld 上跑一遍，不留痕」。`task create` 被工具拒绝——主仓库工作区不干净，
7 个已暂存文件。用户说那不是他暂存的，是 udf 干的，反复出现过好几次。

这句话直接把任务从「验证一个新功能」翻转成「查一个长期缺陷」，结果查出三处相关缺陷加一处
过严检查。

| 关口 | 抓到什么 |
| --- | --- |
| 用户拒绝我的绕过提议 | 缺陷本身——如果按我提的三条路之一动了他的仓库，证据就没了 |
| 代码评审（branch-naming） | 2 条阻断：裸 task-id 查不到台账；merge 的台账判定丢了 workspace 限定 |
| 代码评审（index-pollution） | 2 条阻断：干净检查把未跟踪文件算进去，会让 squash 和 rebase 在用户机器上直接拒绝 |
| 排查途中 | squash 的两个洞——冲突判定读错流、commit 失败不回滚 |

`tests/merge_yes.rs` 的用例数从 12 涨到 22。

## 哪些做法有用

**被规矩挡住时没有绕过去，这是这一段里最值钱的一个决定。**

`task create` 拒绝之后，我列了三条能让验证跑通的路——stash 用户的改动、提交那 7 个文件、
改代码放宽检查——然后一条都没走，把选择权交回去。用户的回答不是选项之一，而是「那是你的
工具导致的」。

如果我当时挑了任何一条：stash 会把证据藏起来，提交会把污染变成用户的历史，改代码会拆掉一道
正确的守卫。**三条路都会让这个反复出现的缺陷继续活着。**

**评审两次都抓到了跟用户真实环境挂钩的问题，不是抽象的代码味道。**

- `branch-naming` 的阻断 1：裸 task-id 查不到台账，实测「分支留在仓库里而命令报成功」。
- `index-pollution` 的阻断 1 和 2：干净检查把未跟踪文件算进去。用户的 `AesWorld` 长期有一个
  `?? workflow/`，这一改之后 `squash` 在他机器上会被无条件拒绝。

两次都是因为评审时问的是「这段代码撞上用户真实的仓库状态会怎样」，不是「这段代码逻辑对不对」。

**回归测试全部做过负向验证。** 这一段一共四条：先回退代码修复确认测试会失败，再装回确认通过。
拿到的失败信息是 `left: "D  feature.txt"`、`left: "AA probe.txt"`、`target worktree is not clean`
——每一条都直接对应一种污染形态，不是「断言不成立」这种没信息的失败。

**发布前门禁从 8 步扩到 12 步，立刻见效。**

| 版本 | Release CI 轮次 | 备注 |
| --- | --- | --- |
| 0.2.0 | 3 轮失败 + 1 次发布后撤回重发 | clippy 版本漂移、8.3 短名、安装器 BOM |
| 0.3.0 | **1 轮过** | 同类问题在 preflight 就被拦下 |

新增的三步（脚本编码、安装器按 `iex` 方式解析、真跑一遍发布说明生成）覆盖的正是 0.2.0 那三次
失败的类型。**把检查从「发出去之后」挪到「打标签之前」，代价是一次改动，收益是每次发布。**

## 哪些做法没用，根子在哪

### 一、我又一次没做到自己声称的隔离

排查时我跑了 `git write-tree`，事前没说。它不改内容，但会写 `.git/index` 的 cache-tree。

这是同一个模式的第二次。上一段是测安装器时把 `USERPROFILE` 指到临时目录，以为隔离了，而
`skill install --global` 走的是系统 API 不看那个变量，真的写了用户四个 provider 目录。

两次的共同点：**我声明了隔离，但没有验证隔离成立就往下做了。** 前一次是没查 API 用哪个来源，
这一次是没想过「只读排查」里的某条命令其实会写。

在别人的仓库上操作时，「这条命令是只读的吗」不能靠印象。`git status`、`git diff`、`git log`
是只读的，`git write-tree` 不是，而它长得像只读。

### 二、审计范围是我自己划的，划小了

`main-repo-index-pollution` 的审计只覆盖「会动插件仓库的命令」。`switch` 动 Junction 和
`state.json`，`build` 动 Host 目录，都被划在外面。

划这个范围的理由是「用户报的是插件仓库被弄脏」，看起来合理。但缺陷的性质是「命令跑完留下了
不属于用户的状态」，这个性质跟被动的是哪个目录无关。**我按症状出现的位置划范围，没按缺陷的
性质划。**

结果是现在仍然不知道 `switch` 和 `build` 有没有同类问题，而它们同样会写用户的磁盘。

### 三、根因藏在唯一一处「跟同类不一样」的实现里，而这个信号一直摆在那

四种合并策略里，`squash`、`rebase`、`ff-only` 都是 shell 出去调真 git，只有 `merge` 用 git2
在内存里算。这个不一致本身就是信号——同一层抽象里有一个成员用了完全不同的机制，要么它有特殊
理由，要么它是没被审视过的历史遗留。

这次是后者。而且我在上一个任务里读过 `merge.rs` 好几遍（改过 `run_inner`、加过台账判定），
每次都从 `merge_branch` 旁边走过去，没问过「为什么只有它不一样」。

## 三种情况分开说

**这次的偶然**：用户恰好在真实仓库上撞到了后果，而且记得这不是第一次。没有这句话，我大概率
会换一个干净的插件把验证跑完，缺陷继续留着。

**这个项目的特点**：udf 的每条写命令都作用在**用户自己的 git 仓库**上，而不是它自己的数据。
这类工具的缺陷有一个共同形态：不是崩溃，是**留下用户没做过的状态**。用户不会报「工具坏了」，
会报「我的仓库怎么脏了」，中间隔着一层归因。

**能推广到流程上的**：

- 被自己的守卫挡住时，先问「这个守卫是不是对的」，再问「怎么过去」。守卫拦住你，往往说明
  它拦对了。
- 在别人的资产上操作前，逐条确认命令是不是真的只读，不靠命令名字判断。
- 同一层抽象里有一个成员用了跟其他成员完全不同的机制，把它当成待查项，不当成风格差异。

## 改进

| 改进 | 能带来什么 | 风险 | 谁做 | 怎么验证有效 |
| --- | --- | --- | --- | --- |
| 把审计断言推广到 `switch` 和 `build`：命令跑完，用户的磁盘上不该留下不属于他的状态 | 覆盖这次划在范围外的两条路 | 这两条动的是 Junction 和 Host，断言不能照抄 git 那套，要另想判据 | 下一个任务，单独开一个 | 断言写出来之后，先回退到当前代码跑一次，看它抓不抓得到东西 |
| 在别人仓库上操作前，把要跑的命令列出来标注读写属性，再动手 | 堵住「声称隔离但没验证」这个重复了两次的模式 | 会让排查慢一点 | 执行者 | 下次在用户资产上排查时，回复里应该有这份清单 |
| 遇到「同一层抽象里唯一不一样的成员」就记一笔待查 | 这次的根因就是这么藏了很久 | 会产生一些查完没问题的待查项 | 执行者，用 `aes-todo` | 看下一段有没有因此提前发现问题 |

三条都是执行时的做法，不改 Skill 或协议。要写进规则得另开任务走 `aes-writing-skills`。

## 这份复盘自己的局限

**没有度量数字。** 这个仓库没装 `collect_metrics.py`，1.3 的工具也不再提供 `collect-metrics`。
所有结论靠提交记录、记录版本链、CI 运行历史和测试计数。

**「反复出现好几次」只有用户的证词，没有量化。** 我没有去翻他各个插件仓库的 reflog 统计这个
缺陷到底发生过多少次、影响过哪些仓库。修复也不回溯清理已经发生的污染，所以那些残留还在。
